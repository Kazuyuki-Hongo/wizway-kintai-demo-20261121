# 設計

## 前提

動機は proposal.md の「なぜ」。いまの更新は Lambda ごとの `/tmp` に閉じている。

## 目標 / 対象外

**目標:**
- 保存と、そのあとの読み取りが別の実行環境でも、同じ行が見える
- 初期データは 2026-11-02 から 2026-11-20 まで。11月1日と21日以降は空
- 空の日は、条件を満たす保存で行を作る

**対象外:**
- DynamoDB と RDS
- 同時保存のマージ

## 決定事項

### 1. 共有ファイルは非公開 S3 の SQLite 1つ

`template.yaml` に非公開バケットを足し、Lambda の環境変数 `KINTAI_DB_BUCKET` と `KINTAI_DB_KEY` で場所を渡す。読み取りの前にそのオブジェクトを `/tmp` へ取る。無いときは同梱の `attendance.db` をアップロードしてから使う。更新が成功したあと、`/tmp` のファイルを同じオブジェクトへ戻す。

テストとローカルは `KINTAI_RUNTIME_DB` の一時ファイルのままにする。S3 は呼ばない。

代替として実行環境を1つに制限する案は取らない。環境が入れ替わった瞬間に、他の人の入力が初期データへ戻る。

### 2. 空の日は INSERT する

その社員・その日の行が無いときは `UPDATE` せず `INSERT` する。日付がその月に無いときと、社員が無いときは、これまでどおり行を作らない。

### 3. 初期データの範囲

2026-11-02 から 2026-11-20 までを3人とも入れる。社員1の 11月2日から5日は、8時間、9時間、退勤なし、欠勤のままにする。2026-11-01 と 2026-11-21 から 2026-11-30 は行を作らない。画面でもその日は入力できる。

## リスク / トレードオフ

- [同時の保存が後勝ちになる] → デモの順に保存する使い方を想定する。同時編集のマージはしない
- [古い共有ファイルが新しい初期データを隠す] → キーを変えるか、オブジェクトを消すと、次の読み取りで同梱の初期データから作り直す

## 移行手順

1. シード、API、画面、template の順で変える
2. アカウントが本番勤怠でないことを確認してから、スタック `wizway-kintai-demo` を更新する
3. 載った URL で、11月20日までが入っていて、21日が空で、保存のあと他の社員の行が残ることを確認する
