# 変更提案

## なぜ

管理者で個別の勤怠を開くと、API が共有 SQLite の中身をリクエストのたびに S3 から取り直す。ファイルは約 40KB だが、128MB の Lambda が同じ往復をログイン、社員一覧、日ごとの行、月の合計で繰り返すので、読み込みが遅い。

## 背景

共有ファイルは、学習用アカウントの非公開 S3 にある SQLite 1つである。読む直前に `/tmp` へ全体を上書きし、保存が成功したあとだけ同じオブジェクトへ戻している。実行環境が分かれるため、`/tmp` だけを正本にすると、環境が入れ替わったときに他の人の入力が初期データへ戻る。

## 目的

オブジェクトが変わっていないあいだは中身を取り直さず、変わった次の読み取りでは保存した行を返す。別の実行環境で保存した行も、次の読み取りで見える。

## 変更内容

- 実行環境は、共有オブジェクトの識別子（ETag）を覚えておく
- 識別子が同じあいだは、`/tmp` にあるファイルを使い、中身は取らない
- 識別子が違えば中身を取り直し、その内容を次の読み取りに使う
- 保存が成功して共有ファイルを戻したあとは、覚えていた識別子を新しいものに合わせる
- テストとローカルは、これまでどおり `KINTAI_RUNTIME_DB` の一時ファイルを使い、S3 は呼ばない

## 対象能力

### 新規の能力

- なし

### 変更する能力

- なし

画面から見える勤怠の要件は変えない。保存した行は次の読み取りに出る、といういまの振る舞いを保ったまま、変わっていない共有ファイルの中身を取り直さない。仕様の差分は作らない。

## スコープ

- 共有 SQLite を読む API（ログイン、社員一覧、日ごと、合計、全員の勤怠、CSV）
- 保存が成功したあとの、共有ファイルへの書き戻し

## 非スコープ

- 数秒のあいだ S3 を見ずに `/tmp` を信じること
- 日ごとの行と合計を1回の通信にまとめること
- Lambda のメモリサイズを上げること
- DynamoDB、RDS、常時起動のコンテナ
- 画面の API の形、区分、合計の式
- 進行中の `sql-practice-schema-and-demo-error`（画面と読み書き API は変えない変更）
- 本番勤怠リポジトリ、本番 DB、本番の勤怠と同じ AWS アカウント
- 実在の社員名、給与、住所、生年月日

## リスク

- 覚えていた識別子がずれると、他の人の保存が次の読み取りに出ないか、古い `/tmp` を使い続ける
- 書き戻しに失敗したあと、実行環境のファイルと S3 がずれたままになる
- 同時の保存は、今どおり後から書き込まれた共有ファイルが残る
- 画面が API を複数回呼ぶことと、128MB のままでいることは変えない。待ちがゼロになるわけではない

## 影響範囲

- `backend/app.py`。共有ファイルの取得と書き戻し
- S3 を模したテスト。ローカルの `KINTAI_RUNTIME_DB` のテストは S3 を呼ばない
- 画面、`template.yaml` の構成、本番勤怠のアカウントは変えない。デプロイするときは学習用アカウントだけを確認する
